## Research
- Start with what the repo states directly: README files, manifests, workspace and lockfiles, build/test/lint/format/typecheck/codegen config, CI workflows, task runners, pre-commit hooks, existing instruction files (`AGENTS.md`, `CLAUDE.md`, `.cursor/rules/`, `.github/copilot-instructions.md`), and `ruth.json`.
- If the structure is still unclear, read a few files that show how things connect: entrypoints, package boundaries, the main execution path.
- When docs and scripts disagree, trust the scripts. Write down only what you confirmed.

## What's worth recording
- Exact commands, especially surprising ones, and how to run one test, one package, or a quick check.
- Command order when it matters, such as lint before typecheck before tests.
- Package boundaries, which directories own what, and the real entrypoints.
- Toolchain quirks: generated code, migrations, build output, env loading, dev servers, deploy steps.
- Test quirks: fixtures, required services, snapshots, slow or flaky suites.
- Rules from existing instruction files that still hold.

## Asking
Ask the user only about things the repo can't answer, like unwritten team conventions or release habits. Use the `question` tool once, with a short batch.

## Writing
- Short sections and bullets. A simple repo gets a simple file.
- Leave out general advice, tutorials, file trees, obvious language conventions, guesses, and anything better kept in a file referenced from `ruth.json` `instructions`.
- If `AGENTS.md` already exists at `${path}`, edit it in place: keep what's verified and useful, remove what's stale or vague, and bring it in line with the code as it is now.
