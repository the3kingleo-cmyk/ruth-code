Review the code changes described below and report problems worth fixing.

Input: $ARGUMENTS

## What to review
- No input: the uncommitted work. Run `git status --short`, `git diff`, and `git diff --cached`, and read any new untracked files in full.
- A commit hash: `git show $ARGUMENTS`.
- A branch name: `git diff $ARGUMENTS...HEAD`.
- A pull request URL or number: `gh pr view $ARGUMENTS` and `gh pr diff $ARGUMENTS`.
If the input doesn't fit neatly, use your judgment.

## Understand before judging
A diff alone can mislead. Read each changed file in full so you see the surrounding logic, error handling, and conventions. Check style or convention files such as `AGENTS.md` or `.editorconfig` when they exist.

## What to look for
- Bugs first: wrong logic or conditions, off-by-one errors, missing or misplaced guards, unhandled empty or null input, race conditions, security holes, and errors that get swallowed or escape uncaught.
- Fit: does the change follow the codebase's patterns, reuse its existing helpers, and avoid needless nesting?
- Performance, only when it's clearly a problem, like quadratic work on unbounded data or blocking I/O on a hot path.
- Behavior changes, especially ones that look unintended.

## Be sure
- Review only what changed, not older code nearby.
- Confirm a bug before calling it one. Investigate with the Explore agent, docs, code search, or web search. If you still can't confirm it, say you're not sure.
- Describe the realistic situation where the problem shows up, not hypotheticals.
- Don't nitpick style. Flag a convention issue only when the code clearly breaks it and the fix is simpler.

## Report
For each finding, give the file and line, what's wrong, when it happens, and how serious it is, without overstating. Keep it plain and brief, and skip praise or filler. If you find nothing worth fixing, say so in one line.
